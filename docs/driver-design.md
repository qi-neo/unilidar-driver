# 如何编写一个激光雷达驱动

这篇文档不针对某一款雷达，讲的是写传感器驱动时反复会用到的思路。
文中所有"坑"都来自 `unilidar_driver` 开发过程中真实撞到的，
不是泛泛而谈的最佳实践。

---

## 一、先想清楚：驱动到底在"驱动"什么

多数人第一步就搞错了边界，把下面这些全塞进驱动：

- 坐标变换到车体 / 机体
- 地面提取、去噪、聚类
- 时间戳对齐、多传感器融合
- 业务逻辑（比如"提取轮迹高程剖面"）

**驱动只负责一件事：把不可信的字节流，变成可信的数据结构。**
到"给出 N 个点，每个点有 x/y/z/强度 + 一个时间戳"为止，再往上一层都不归它管。

判断标准：如果明天换了一块雷达，你的驱动要改；如果换的是车或者算法，
驱动**一行都不该动**。边界划对了，驱动才能被复用、被单独测试。

本项目里 `unilidar_driver` 只负责产出 `/unilidar/cloud` 与 `/unilidar/imu`，
而"从点云里提取路面高程剖面"在 `suspension_preview_v2`，"用姿态做闭环控制"在
`suspension_control_v3` —— 三个包各自可独立编译测试。

---

## 二、四层架构

```
   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
   │ 传输层    │ → │ 协议层    │ → │ 解码层    │ → │ 适配层    │
   │ UDP/串口  │   │ 帧定界    │   │ 几何换算  │   │ 消息/QoS  │
   └──────────┘   └──────────┘   └──────────┘   └──────────┘
    收字节          切成完整帧       变成有物理量     ROS 话题/TF
                     + 校验          意义的数值
```

### 为什么这样切

关键收益是**前三层不依赖 ROS**。这带来三个直接好处：

1. 没有装 ROS 的机器上也能编译、能跑断言，开发时不用等硬件也不用开 RViz；
2. CI 里不装 ROS 也能测核心逻辑；
3. 换传输方式（UDP → 串口 → 文件回放）只动第一层，协议与解码不动。

对应到代码，本项目的分层是：

| 层 | 文件 | 依赖 |
|---|---|---|
| 传输层 | `udp_receiver.{hpp,cpp}` | POSIX socket |
| 协议层 | `protocol.{hpp,cpp}`、`packet_parser.{hpp,cpp}` | 纯 std |
| 解码层 | `frame_decoder.{hpp,cpp}` | 纯 std + `<cmath>` |
| 适配层 | `unilidar_driver_node.cpp` | rclcpp、sensor_msgs、tf2 |

## 三、各层的做法与坑

### 3.1 传输层：只收字节，不关心内容

**该做的**

- UDP：`bind` 到指定本机地址与端口；设 `SO_RCVTIMEO`，让 `recvfrom` 能返回而不是永久阻塞；
- 串口：**必须 `cfmakeraw`**。不关行规程的话，0x0A 会被当成换行、流控字符会被吞，
  二进制协议直接被打断。这是 v1 审查里排在最前的 P1 级问题；
- 让上层能拿到**来源地址**，便于"只认这一台雷达"。

**坑：`recvfrom` 返回 0 不是 EOF。**
UDP 是无连接的，返回 0 只表示超时内没数据，不代表连接断开。
把 0 当 EOF 会导致驱动莫名退出。

**坑：缓冲区上限。**
解析不出一帧时（波特率不对、对面根本不是雷达），缓冲区会一直涨。
必须设上限并整体清空，否则内存被慢慢吃光——本项目在 `PacketParser`
里用 `max_buffered_` 做了这件事，并单独计数供诊断。

### 3.2 协议层：帧定界是核心难点

这是整个驱动最值得花心思的地方。定界有三种思路：

**方式一：定长帧。** 最简单，一个包长度写死。
问题：固件一改长度就全错，而且你无法从数据本身发现"错了"——
只会得到一堆乱码点云。

**方式二：长度字段。** 报文里带一个"本帧多长"的字段。
问题：长度字段自己也可能损坏。按损坏的长度去切，会把后续所有帧全部带偏。

**方式三：定界标识 + 校验和。** 头部有魔数，尾部有标识，中间有 CRC。
最稳，因为校验和是**数据的函数**，坏了一定对不上。

**推荐组合：头部标识 + 长度字段（仅用于确定读多少）+ 尾部标识 + CRC32。**

本项目用的是这一套，关键在**角色分工**：

- **长度字段只决定"从缓冲里取多少字节"**，不参与"这帧对不对"的判断；
- **尾部标识 + CRC32 才是判据**。CRC32 是 32 位校验，随机字节对齐的概率约 2⁻³²，
  足以把噪声拒掉。

#### 为什么不要硬编码整包长度

这是本项目最贵的一课。官方协议头文件 `unitree_lidar_protocol.h` 里写着：

| 项 | 注释写的 | 按字段实算 |
|---|---|---|
| 3D 点云数据段 | 1012 B | 1020 B |
| 3D 点云整包 | 1036 B | 1044 B |
| IMU 数据段 | 132 B | 56 B |
| IMU 整包 | 156 B | 80 B |

**注释和它自己的字段定义差了一截。** 如果照注释写死长度，
轻则所有帧被判非法丢弃，重则按错误长度切缓冲、后续帧全部错位。
（错位后的表现特别阴间：偶尔能解出点，但点是乱的，很容易让人误以为是几何公式写错。）

#### 必须支持重同步

字节流不会总是从帧头开始：串口可能半路接入，UDP 可能丢包。
解析器要能在帧头损坏时**跳过垃圾字节重新找头**，并且：

- 找不到帧头时，保留最后 3 字节（可能是下一个帧头的前缀），其余丢弃；
- 失败路径也要计数。**"悄悄丢数据"是驱动最难查的 bug**，
  必须把 `resync_bytes`、`bad_crc`、`bad_tail` 都暴露出来。

#### 序号连续性

报文里通常有自增序号，用于发现丢包。
注意：**只在同一种报文类型之间比较**。点云和 IMU 各有各的序号序列，
混在一起比会永远误报丢包。所以状态要按 `packet_type` 分开存。

序号异常要分三类记，含义不能混：
`seq > last + 1` 是丢包（`seq_gaps`）、`seq == last` 是重复包、`seq < last`
是乱序（`out_of_order`）。重复包在 CRC 校验通过后直接丢弃——同一扫描线被
计两次比丢一帧更难查；乱序包本身数据有效，仍交付但顺序不可信。

### 3.3 解码层：把帧变成有物理意义的量

**用 `#pragma pack(1)` 定义镜像结构体。**
不打包的话，编译器会按成员对齐插入 padding，同一份头文件在不同平台
偏移不同。打包后偏移完全确定。

**越界保护三道。**

以点云为例，报文里带一个 `point_num` 字段，后面跟着最多 300 个点的数组：

1. `point_num > 300` → 直接判非法，否则会读越界；
2. 包长度必须够读到 `point_num` 本身；
3. 包长度必须够读到 `point_num` 个点（`3 × point_num` 字节）。

**包比预期短时，先清零再拷。**
```cpp
LidarPointDataPacket pkt{};                        // 整体清零
const std::size_t copy_len = std::min(frame.size(), sizeof(pkt));
std::memcpy(&pkt, frame.data(), copy_len);         // 只拷实际有的
```
否则读不到的部分是上一次调用的栈残留，会变成随机点。

**几何换算公式必须逐字对照官方实现，并且能用退化案例验证。**
本项目点云的 x/y/z 涉及双棱镜机构的四个标定角（beta/xi/alpha/theta），
公式来自官方 `parseFromPacketToPointCloud`。验证方法：
把标定参数全置 0，此时几何退化成"YZ 平面上的极坐标"，
`angle_min = 30°` 时解出的 z 必须精确等于 `sin(30°) = 0.5`。
这种可手算的案例比"看起来差不多"可靠得多。

**逐点时间/环号同理：先核对官方语义，再决定字段怎么填。**
本项目补逐点 `time` / `ring` 时，先逐行读了官方
`parseFromPacketToPointCloud`，发现两个容易凭字段名猜错的点：

- `time` 不是"按有效点个数递增"，而是 `time_relative` 在 `for` 的递增表达式
  里**每处理一个 j 都加一次** `time_increment`（被 `continue` 掉的无效点也占
  一步），所以偏移恒为 `j × time_increment`，剔除无效点不会压缩时间轴；
- 官方单包内每点 `ring` 写死为 `1`（一个点云报文 = 一条扫描线，整圈由
  `cloud_scan_num` 条线拼成，官方 README 示例是 `ringNum = 18`、首条线
  `ring = 1`）。协议里根本没有"这条线是第几环"的字段，只能由拼帧方按顺序给。

这类字段的验证要把"公式"和"范围"一起断言：时间单调且步长正确、
无效点不压缩时间轴、两种时间戳模式基准正确、拼满一圈后 ring 恰为
`1..cloud_scan_num` 且同一线内点序号的分布符合预期。官方发布的是预编译库时，
除了读随源码分发的参考实现，还可以反汇编确认（本项目就是这样确认官方
二进制里 `ring` 实际写死为 1、线序只在累加器计数里的）。

### 3.4 适配层：唯一碰 ROS 的地方

**QoS 必须匹配，否则就是"明明在发却收不到"。**
这是本项目第二个真实的坑：官方节点按 RELIABLE（`create_publisher(topic, 10)`）发布，
而消费方 `suspension_control_v3` 用 `SensorDataQoS`（BEST_EFFORT）订阅。
**RELIABLE 与 BEST_EFFORT 不兼容**，两边都跑得好好的，就是一个字节都传不过去，
而且没有任何报错。

规律：**传感器数据发布方通常用 BEST_EFFORT，订阅方就要用 `SensorDataQoS`**，
不能想当然用默认 QoS。

**消息字段布局要考虑下游怎么消费。**
下游常用 `pcl::fromROSMsg<pcl::PointXYZ>` 转换，它按字段名拷贝，
所以 `x, y, z` 必须在，多一个 `intensity` 无妨（L1 是 4D 雷达，灰度是增量信息）。
但如果你把 `x` 放在第二个字段，或者用了非 float32，下游直接转不出来。

**加字段要重算 `point_step` 与对齐。**
本项目给 PointCloud2 补 `time`(FLOAT32) 和 `ring`(UINT16) 时，字段从 4 个变 6 个，
`point_step` 不能只按"字段大小相加"得 22——那样下一个点的 `x` 会落在
`2 mod 4` 的地址上，任何按 float 读下一点的下游都会读到未对齐数据。
正确做法是补 2 字节 padding 取 24（4 的倍数），并在代码注释和 README 里
把每个字段的偏移写清楚；写入时逐字段 `memcpy`，不要假定消息缓冲区本身对齐。

**静态外参和动态姿态要分开广播。**
- `lidar → imu` 这种固定安装关系：用 `StaticTransformBroadcaster`，发一次就够；
- IMU 实时姿态：用普通 `TransformBroadcaster`，每帧都发。
本项目实测官方节点把两者都用普通广播器每帧重发，浪费且没必要。

**参数与 yaml 数量要对齐。**
用脚本比对 `declare_parameter` 的个数和 yaml 里的键，防止漏配——
漏配的参数会静默使用默认值，排查起来很痛。

## 四、可验证性：最容易被跳过、但最值钱的部分

驱动的宿命是"接上硬件才知道对不对"。所以必须**主动留下脱离硬件的验证路径**，
否则每次改驱动都要搬着一台雷达调试。

按成本从低到高，七件事值得做：

**1. 合成报文做 round-trip 自检。**
自己按协议构造一帧报文（算好 CRC），喂给解析器，断言能解出来；
再故意改坏一个字节，断言被拒。覆盖：

- 正常帧 / CRC 篡改 / 帧尾篡改 / 长度字段越界
- 数据分批到达（模拟 UDP 分片或串口流式）
- 前面有垃圾字节（重同步）
- `point_num` 越界、包长不足
- 序号跳变、重复包、乱序包
- 逐点时间单调性/步长、两种时间戳模式基准、ring 范围与拼帧后的分布
- CRC32 对**已知测试向量**：`"123456789"` 应得 `0xCBF43926`

本项目 `decoder_selftest.cpp` 有 151 项这样的断言。

**2. 变异测试，验证自检本身有效。**
写完自检一定要确认它抓得住错——否则是假绿灯。
做法：把实现里的关键处故意改坏，重编译，看断言是否失败。
本项目试过三处：

| 改坏什么 | 结果 |
|---|---|
| CRC 初值 `0xFFFFFFFF` → `0x00000000` | 被 CRC 向量断言抓住 |
| 点云 `z = C + a` → `z = -C + a` | 被"仰角 30° 时 z 应为 0.5"抓住 |
| 成功路径漏记 `resync_bytes` | 被重同步计数断言抓住 |

**3. 实测定界探针。**
文档不可信时（本项目的字节数注释就是反例），让用户能在真机上 5 分钟拿到真相。
`udp_probe` 不做任何解码，只回答三个问题：有没有收到包、真实整包多长、
CRC 判据是否成立。汇总里直接标注"是否与本驱动预期一致"。
**这比让用户改代码试长度靠谱得多。**

**4. 明确写出未验证范围。**
README 里分清"已验证"和"未验证"，别让读的人误以为全测过了。
本项目就明说了 ROS 节点编译与真实雷达未验证，需要在目标机 `colcon build`。

**5. 满码率压力灌入，专打"坏帧之后"。**
单发坏帧的自检有个盲区：坏帧后面**不接**好帧时，解析器的恢复路径
（丢一个字节、重新找帧头）走不到"恢复之后还能不能解出下一帧"。
本项目用 PTY 主端按满码率灌合成报文，在流量里掺垃圾与伪帧头、周期性
制造读背压，断言灌入帧数 == 解出帧数——`packet_parser` 一个真 bug
（坏帧分支 `continue` 前没重置扫描游标，每次坏帧后再丢一整帧）就是
这样抓到的：151 项报文自检与 64 项串口自检当时都是全绿的。
**教训：自检的用例形态要贴着真实链路最可能的形态设计，而不是只图好写。**

**6. 边界与真实量级，别只测"典型值"。**
后来又抓到两个 P0，共同点是 151 项自检当时全绿却一个没抓到，因为用例只
覆盖了典型长度与典型数量级，而缺陷恰好在边界上：

- **极短报文**：`packet_size` 合法下界 24（无数据段），但读序号要 16 字节，
  24..39 字节的包会越界读。原先只测了正常长度的包。
- **真实 Unix 时间量级**：逐点 `time` 用 float32 存绝对秒，在 1.7e9 量级
  量化步长是 128 秒，300 个点全塌成一个值。原先用例的时间戳都取 0 或
  1000.5 这种小值，float32 精度足够，缺陷被掩盖。

**教训：数值类字段要用真实量级做用例（时间戳就用 1.7e9，别用 0），长度类
字段要扫合法区间的两端（尤其下界）。**

还有一条：**不要指望 sanitizer 兜底**。libc++ 的 container-overflow 标注在
`-O1` 及以上会被优化掉（实测 `-O0` 报、`-O1`/`-O2` 不报），而 CI 的 sanitizer
job 正是 `-O1`。内存类缺陷的回归用例要转成可观测行为来断言，见
`decoder_selftest.cpp` 的 `[10] P0 缺陷回归`。


**7. 把主循环从框架里抽出来，让"实时性"可测。**
节点里真正有行为的只有「收包 → 定界 → 解码 → 拼帧」这一段。它埋在 ROS 节点
里时，吞吐、单轮耗时、缓冲增长全都只能靠真机观测；抽成不依赖 ROS 的
`DriverLoop`、把发布当回调注入之后，这一段就能在普通机器上灌满码率实测——
节点与自检跑的是同一份代码，也就不存在两套逻辑各自漂移。

## 六、本项目的一个完整例子

`src/unilidar_driver` 就是按上面这套做的，规模不大（核心四个文件约 700 行），
可以作为参照：

```
src/unilidar_driver/
├── include/unilidar_driver/
│   ├── protocol.hpp        帧结构（pack 1）+ CRC32
│   ├── packet_parser.hpp   字节流 → 整包，支持重同步
│   ├── frame_decoder.hpp   整包 → 点云 / IMU
│   ├── serial_receiver.hpp POSIX termios 串口收包（L1 实物默认路径）
│   ├── driver_loop.hpp     主循环：收包 → 定界 → 解码 → 拼帧（不依赖 ROS）
│   └── udp_receiver.hpp    POSIX UDP 收包
├── src/                    以上实现 + unilidar_driver_node.cpp（唯一碰 ROS 的文件）
├── examples/
│   ├── decoder_selftest.cpp  151 项断言的离线自检
│   ├── serial_receiver_selftest.cpp 串口接收自检（PTY 虚拟串口），64 项断言
│   ├── serial_stress_selftest.cpp 串口压力自检（PTY 满码率灌入），14 项断言
```
